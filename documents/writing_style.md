# 書き方の基本

この文書は、全体の書き方をそろえるための基準です。章や前書きで迷ったら、まずここに戻ってください。

## 基本の型

文章は、読者が抱きやすい疑問や困りごとから始めます。読者が「なぜこれを知る必要があるのか」を理解できる問題（why）を示し、その問題を解くための理論や仕組み（what）を説明します。具体的な解決策や実装がある場合は、最後に手順やコード（how）を示します。

読者が知っていることを並べるのではなく、読者が疑問を持つ順番に説明してください。読者が共感し、内容を理解しやすい身近な場面や失敗から書き始めると、説明の必要性が伝わります。

作者の経験や失敗は、読者の理解に役立つ範囲で使います。前書きでは、作者がなぜこのテーマに取り組んだのか、どのような失敗や発見があったのかを具体的に書いて構いません。ただし、作者の経験を中心に据えすぎず、読者が何を学べるのかが分かるようにしてください。

技術説明では、次の順番を基本にします。

1. 読者が困っている場面や、自然に抱く疑問を書く（why）。
2. その疑問に答える理論や仕組みを説明する（what）。
3. 必要に応じて、解決策の手順や実装を示す（how）。
4. 作者の経験や失敗を添える場合は、読者が理解したり実践したりする助けになる形にする。

たとえば、次のように書きます。

> 自作キーボードでは、配線が合っているように見えるのにキーが反応しないことがあります。なぜこの問題が起きるのでしょうか。
>
> 原因を切り分けるには、電源、配線、ファームウェアを別々に確認します。それぞれがどの役割を持つかを理解すると、確認する順番も決めやすくなります。
>
> まずテスターで導通を確認し、次にファームウェアのキーマップを確認します。問題が見つかった箇所を直してから、もう一度動作を確認してください。

## 作者と読者の扱い

本文では、一人称として「作者」を使い、読者には「読者」と表現します。「僕」「君」などの呼びかけは使いません。作者と読者を対立させたり、作者が一方的に語りかけたりするのではなく、読者が自分の問題として読み進められる文章にしてください。

作者の経験は、次のように扱います。

- 作者が実際に経験した失敗や判断を書く。
- その経験が、読者の疑問や実践にどう役立つのかを明確にする。
- 作者を必要以上に格好よく見せず、事実とそこから得た知見を示す。
- 作者の金銭的な制約や不安などを書く場合も、読者が状況を理解するために必要な範囲にとどめる。

読者については、次の前提を置きます。

- キーボード作りに興味がある。
- 普段はキーボードを使っているが、中身はよく知らない。
- ソフトウェアエンジニアとして、理屈が分かれば手を動かせる。
- 最初からすべてを知っているわけではないが、手順が見えれば試せる。

読者を子ども扱いせず、前提知識を過剰に要求もしないでください。読者が疑問を持つのは自然なことです。その疑問を出発点にして、必要な知識を順番に説明します。

## 口調

- 本文は丁寧語（です・ます調）を基本にします。
- 作者の経験を語る場合も、乱暴な口語やくだけすぎた表現は避けます。
- 読者への呼びかけは「読者」を使い、「君」などの表現は使いません。
- 作者と読者の登場比率は設定しません。作者の経験を出す量ではなく、読者の理解に必要かどうかで判断します。
- 事務的になりすぎないよう、具体的な場面、失敗、判断の理由を示します。

## 過去の経験と成長の見せ方

過去の作者は、格好よく書く必要はありません。何に困り、何を見落とし、どのように解決したのかを具体的に書くと、読者は問題の構造と解決までの道筋を追いやすくなります。

書き方は、次の順番を基本にします。

1. 作者が詰まった状況を書く。
2. 何を見落としていたのかを説明する。
3. 問題を解くための理論や仕組みを説明する。
4. 現在ならどのように判断し、実装するのかを書く。
5. 読者が同じ問題に出会ったときの確認方法を示す。

成長は、気持ちではなく差分で示します。「成長した」とまとめるのではなく、「以前は分からなかったが、いまは切り分けられる」のように、何がどう変わったのかを書いてください。

## 書くときの軸

- 各節で、読者が抱く疑問や困りごとを明確にする。
- why、what、howの順番が崩れていないか確認する。
- 理論を説明するときは、実装や具体例とのつながりを示す。
- 実装を示すときは、なぜその方法を選ぶのかを説明する。
- 作者の経験は、読者の共感や理解に役立つ箇所へ配置する。
- 事実があるなら事実を優先する。
- 飾りたいだけの比喩は使わない。
- 読者が次に何を確認し、何を実行すればよいか分かるようにする。
- 前書きでは作者の動機を十分に伝える。ただし、本書で読者が得られる知識や判断材料も示す。

## 図とコードの出し方

- 画像を入れる場所は、後で差し替えやすいようにコメントで明示します。
- 配線図は、あとで `wokwi` で作る前提で、いまはコメントアウトしたコードも残します。
- `wokwi` 用のコードや本文中のコードは、`codes/` ディレクトリにある実装を抜き出して使います。
- コードを引用するときは、最終的なまとめのコードを除いて、原則5行を超えないようにします。
- 5行に収めるために、説明に不要な部分は省きます。必要なら、章の途中では短い断片だけを見せて、最後にまとめて示します。
- まとめのコードだけは例外にして構いませんが、それ以外は長くしないでください。

## 迷ったときの判断

次のどちらかで迷ったら、後者を選びます。

- きれいに書く / そのときの実感を書く
- 強く見せる / 事実をそのまま書く
- 作者の経験を増やす / 読者の疑問を解く
- 理論を先に詰め込む / 読者が必要とする理由から説明する
- 抽象的にまとめる / 何が起きたかを明示する

この文書の目的は、作者の声を強く出すことではありません。読者が問題の理由を理解し、仕組みを学び、必要なら自分で実装できる文章にそろえることです。
