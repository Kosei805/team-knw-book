# Chapter Review

技術書の章を、読者が「困りごとを自分ごとにする → 解決策の理屈を理解する → コードで実装できる」という順に読めるかレビューする。本文を書き換えず、問題点と修正優先順位を報告する。

## Workflow

1. 対象章、対応する骨子、目次、参照コード、直前・直後の章を読む。Re:VIEW原稿では`nl -ba`で行番号を取得する。
2. 章全体の到達点と、各節が解決する問題を一文で要約する。
3. 各節を`why -> what -> how`の順に分解する。
4. 問題提起から理論、理論からコードへの因果が途切れている箇所を、重要度順に指摘する。
5. `git diff`やビルド結果が必要な場合は、内容レビューと混ぜず、末尾の検証欄で扱う。

## Evaluation Criteria

### Why: 問題提起

- その技術を使わないと何が起きるかを、読者が想像できる具体的な場面で示しているか。
- 「入力されない」「複数回入力される」「状態が戻らない」のように観測できる失敗になっているか。
- 問題が、対象読者の作業や失敗と結び付いているか。抽象的な「重要性」「必要性」だけで終わっていないか。
- 比喩を使う場合は、技術的な対応関係が崩れていないか。比喩だけで説明せず、直後に実際の問題へ戻す。

### What: 解決策の理屈

- 解決策が専門用語の紹介で止まらず、なぜ`why`の問題を避けられるか説明しているか。
- 状態、入力、出力、イベント、データ形式など、読者が頭の中で追う対象を明示しているか。
- 「Aが入力される」なら、状態遷移やデータの流れを順序立てて説明しているか。
- 用語を出した直後に、役割と必要性を説明しているか。HID、キーコード、デバウンスなどを未定義のまま連続させていないか。

### How: 実装

- 説明した理屈に対応するコードがあるか。
- コードの各部分が、入力、判定、状態更新、出力のどれを担当するか明確か。
- 完成コードだけでなく、失敗する最小コードと、なぜ失敗するかが必要な箇所にあるか。
- 配線、設定、ライブラリ、実行順序、観測結果が、初心者でも再現できる粒度で示されているか。
- コードの説明が実装の逐語訳になっておらず、理論上の役割と結び付いているか。

## Section Review

各節について次の順で確認する。

1. 節の冒頭に、読者が遭遇する失敗や違和感があるか。
2. その失敗の原因を、専門用語を導入しながら説明しているか。
3. 解決策を使うと、なぜ失敗を避けられるのかが自明になるまで分解しているか。
4. 理論に対応するコード、配線、設定、実行結果があるか。
5. 節の終わりで、次の節へ進む理由が生まれているか。

`why`がない場合は「説明が抽象的」とせず、読者が見る具体的な失敗例を提案する。`what`がない場合は、用語とコードの間にある状態遷移・データ形式・因果を特定する。`how`がない場合は、必要なコード断片、配線、確認手順を指摘する。

## Chapter-Level Review

- 冒頭で完成物、読者の到達点、最初に解決する失敗が分かるか。
- 各節が独立した説明ではなく、前の節の成果を次の問題解決に使っているか。
- 単純な構成から複雑な構成へ進む理由があるか。
- 章末で、読者が何を観察・判定できれば完成なのか明示しているか。
- 次章への導入が、単なる予告ではなく、この章で得た制約や未解決問題から自然に出ているか。

## Technical Accuracy

構造レビューでも、説明とコードの不一致は指摘する。特に次を確認する。

- 本文のコード例が実際の参照コードと一致しているか。
- 「押す」「離す」「送る」「安定する」などの言葉が、実装の状態遷移と一致しているか。
- 電気的な状態（High/Low）とプログラム上の値（`True`/`False`）の対応が明示されているか。
- USBや通信では、送信側の状態、データ形式、受信側の解釈が混同されていないか。
- 一般化しすぎた説明や、環境依存の挙動を断定していないか。

## Output Format

レビュー結果は、問題点を先に、重大度順に出す。各指摘には次を含める。

1. 重大度（高・中・低）と短い見出し
2. 原稿のファイルと行番号
3. どの`why`、`what`、`how`が不足しているか
4. 読者がどこで理解を失うか、または何を誤実装するか
5. 修正の方向。必要なら具体的な失敗場面、比喩、説明すべき状態遷移を示す

その後に、次を短くまとめる。

- 構造上うまく機能している節
- 修正優先順位
- 残る検証リスク（ビルド、実機確認、参照コードとの一致など）

本文を直接編集しないよう依頼されていない限り、レビュー中に編集を行わない。指摘は要約ではなく、読者理解・実装再現性・技術的因果に集中させる。
