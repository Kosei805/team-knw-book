# Content First Writing

技術書の前書きや章を書く前に、段落設計と取材を終えるためのスキル。

目的は、もっともらしい本文を先回りして補うことではない。著者だけが答えられる事実を取材し、読者が「自分に必要な本か」「読むと何ができるか」を判断できる文章の材料をそろえる。

## 使う場面

- 技術書の章、前書き、説明文を新規に書くとき
- 既存の前書きが、抽象的な紹介文や雰囲気の説明になっているとき
- 構成や段落の役割を先に決めたいとき

## 基本方針

### 用語の固定

- 「ユーザー」は、この執筆作業を依頼し、質問に答える目の前の相手を指す。
- 「読者」は、完成した本を読む人を指す。取材中に質問する相手ではない。
- 取材の質問は「ユーザー」にする。完成稿では、読者が共感しやすい課題感と、その解決策を伝える。
- 迷ったら、質問文に「ユーザー」と「読者」のどちらを置くべきか確認する。ユーザーの回答を集める質問と、読者に届ける本文を同じものとして扱わない。

1. 本文の核、事実、主張の採否はユーザーが決める。事実が足りなければ文章を書かない。
2. 章を書くときは、必ず対象章の `bone_~.md` を出発点にする。そこに書かれたMarkdownの見出し、順序、箇条書きを章の骨組みとして保持し、その内側だけを肉付けする。
3. 骨子に `?` とだけ書かれた箇所は「何かを入れたいが内容未定」の印である。そこには内容を推測して埋めず、候補を作ったうえで取材し、ユーザーの回答をもとに確定する。
4. 取材の進め方と、完成した文章の型を混同しない。質問を一つずつ行うのは取材のルールであり、完成稿のすべてをQ&A形式にする意味ではない。
5. 前書きでも章でも、本文は読者が共感しやすい課題感を先に置き、その解決策を示し、必要な場合だけ実装や手順へ進む。基本の流れは `why -> what -> how` とする。
6. 質問は一度に一つだけ出す。必要なら A/B/C の候補を添えるが、自由記述を優先する。
7. 段落数を選ぶのは取材の後にする。段落の数合わせのために内容を水増ししない。
8. 技術説明の段落では、読者が「なぜそれが必要なのか」を先に理解できるようにし、その後で「何をするのか」「どう実装するのか」を組み立てる。
9. ユーザーが質問に答えたら、その回答を材料に段落の一部を短く書いて見せる。この時点で `humanizer-ja` を使い、表現を整えながら書く。次の質問に進む前に、方向が合っているかを確認する。
10. 各段落には、課題感、解決策、判断材料のどれを担う段落かを見えるようにする。実装段落は必要なときだけ置く。
11. 執筆中も、段落を起こすたびに `humanizer-ja` を当てて、丁寧語、具体性、温度をその場で整える。書き終わってからまとめて整えるやり方は取らない。

## 前書きと技術説明の使い分け

このスキルには、取材の型と文章の型がある。取材はどちらも「一問ずつ聞く → 回答を短く文章に反映する → 方向を確認する → 次の質問へ進む」で進める。文章の型は、対象によって分ける。

- 前書きは、著者の動機や実感だけで閉じず、読者が自分ごととして受け取れる課題感へ接続する。
- 技術説明は、読者が引っかかりやすい疑問や不安を起点にし、その解決策を先に示す。
- 実装や手順は、解決策の理解に必要な場合だけ続ける。前書き全体や章全体をQ&Aにしない。

骨子にない動機や冒頭の意図を、会話の外から補ってはいけない。必要なら骨子の該当箇所を `?` として取材対象にする。

## `bone_~.md` を使った章の進め方

1. 対象章に対応する `bone_~.md` を読み、Markdownの構造をそのまま一覧化する。見出しの追加、削除、並べ替えはユーザーの了承なしに行わない。
2. 骨子に書かれている内容を「確定した本文」ではなく、「その位置に必要な話題」として扱う。具体例、経験、説明の深さは取材で確定する。
3. `?` の箇所ごとに、そこへ入れられる候補を複数示す。候補を本文として採用せず、ユーザーに一つずつ質問する。
4. ユーザーの回答を受けたら、該当する骨子の位置に入る短い文章の一部を書いて示す。ユーザーが方向を確認した後、次の `?` へ進む。
5. `?` がない箇所でも、骨子の情報だけでは事実・具体例・技術的な根拠が不足する場合は、勝手に補わず、その箇所について一問だけ取材する。
6. 骨子から外れる内容を提案したい場合は、本文に混ぜず「追加候補」として示し、採用するかを質問する。

## 前書きの取材

文章を書く前に、次の項目を必要な順番で一問ずつ確認する。前書きでも、読者が共感しやすい課題感と、それに対して本書が何を差し出すのかを確認する。回答が「楽しい」「学べる」「初心者向け」のように抽象的なら、作業、物、失敗、時系列、固有名詞、数値のいずれかを聞いて掘り下げる。

1. 読者がすでに経験した、またはすぐ想像できる場面・困りごと・違和感は何か。
2. 本で実際に作るもの、触るもの、変えるものは何か。
3. 最初に動いたとき、読者は何を観察できるか。途中の小さな成功は何か。
4. 読後に読者ができること、切り分けられること、説明できることは何か。
5. 本固有の進め方は何か。一般的な進め方ではどこで詰まり、その方法はいつ何を動かして確かめられるようにするのか。
6. 著者自身が経験した失敗、驚き、きっかけ、または完成物の印象的な挙動は何か。
7. 想定読者の開始地点はどこか。必要な知識、環境、道具、時間、許容する失敗を分けて確認する。
8. 扱わない範囲、または別の準備が必要な範囲は何か。
9. 実際の目次に沿った進み方、どこから読めるか、最初に行う具体的な作業は何か。

項目が前書きに必要かどうかはユーザーに決めてもらう。ただし、課題感・作るもの・到達点・方法を選ぶ理由が未確認のまま本文には進まない。
技術説明に使う項目は、読者が実際に引っかかりそうな疑問や不安に変換してから扱う。たとえば「文字はどう送られるのか」「なぜダイオードが要るのか」を先に言葉にし、その答えとして文を組み立てる。
前書きの作者動機や書籍の位置づけも、読者の課題感と自然につながる形にする。作者の経験だけで閉じず、読者の判断材料へ接続する。
骨子を読み取っただけで本文を書き換えず、毎回、取材で得た回答を短い文章に反映してから次の質問へ進む。

## 冒頭を決める

前書きの冒頭候補は、骨子に作者の動機がある場合、その動機を勝手に別の入口へ置き換えない。骨子に `?` がある場合は、最低3本の候補を考えて取材する。

技術章の冒頭候補は最低3本考え、それぞれをユーザーに示して選んでもらう。候補は次のいずれかを材料にする。

- 読者の手元にある物や、よくある作業の具体的な観察
- 著者または読者が経験する失敗や違和感
- 完成物が動いた瞬間、または試して分かる挙動
- 本書の主題へ必然的につながる、著者自身の明確な問い

各候補には、次の二点を添える。

1. 読者にどんな具体的な期待や疑問を生むか。
2. 本書の主題へ何文で、どのようにつながるか。

流行、AI、業界一般、社会一般を入口にする場合は、著者自身の具体的な経験または検証可能な事実を置き、本書の主題へ2文以内で因果をつなげられるときだけ採用する。つなげられない一般論は使わない。

## 段落設計

取材がそろってから、段落数と役割を A/B/C で提案する。基本は `why -> what -> how` の順で組む。すべてを必須にはしないが、欠ける役割があるときは、読者に不要かを確認する。

1. 読者が自分ごとにできる場面、困りごと、違和感
2. その課題に対して本書が示す具体的な解決策や見通し
3. この順序・方法を選ぶ理由と、避けたい詰まりどころ
4. 途中または読後に得られる、判定できる成果
5. 対象読者の開始地点、前提、必要なら対象外
6. 実装や作業が必要なら、その入口と最初の具体的な行動

各段落の設計には、次の三つを必ず記す。

- その段落に入れる、ユーザー確認済みの事実
- 前段までを読んだ読者に、次に何を知りたくさせるか
- 読後に読者が増やせる判断材料

## 本文にする際の規則

- 「学ぶ」「理解する」「触る」「楽しむ」「歓迎する」「安心」「世界」「余地」のような抽象語を、単独で読者価値にしない。対象物、行為、段階、観察可能な結果を添える。置換できなければ削るか、取材に戻る。
- 成果は読者が判定できる動詞で書く。たとえば「設定を書き込む」「配線する」「挙動を変える」「原因を切り分ける」のように表す。
- 「本書は〜の本です」の後には、内容だけでなく、なぜその手順なのかを具体的に続ける。一般的な手順の障害と、本書の進め方でいつ何を確かめられるかを一組で示す。
- 「初心者から経験者まで」のように対象を無制限に広げない。開始条件と支援する不安を分け、必要なら対象外も書く。
- 「コメディ寄り」「気楽に読める」のようにトーンを自己申告しない。著者承認済みの観察、失敗談、比喩、文のリズムで示す。ユーモアは義務にしない。
- 本文は原則として丁寧語で書く。読者への呼びかけとして「君」を使わない。著者を「僕」で固定する書き方もしない。
- 技術説明の見出しや段落の入り口は、読者が引っかかりやすい課題や疑問をそのまま使ってよい。ただし、問いを置くだけで終わらせず、すぐ答えに入る。
- 前書きの見出しや段落の入り口でも、作者の動機だけで閉じず、読者が共感できる課題感へつなげる。
- 実際の目次や執筆済み範囲を確認してから、章の進み方、読了時間、途中から読めるかどうかを書く。未確定の構成は捏造しない。
- 終わりは「世界をのぞこう」のような汎用的な誘いではなく、最初の章で読む人が行う作業、確かめること、または冒頭で置いた問いに接続する。

## 進め方

1. 前書きか章かを確認し、既存本文・目次・制約を読む。以降、質問の宛先はユーザー、本文で答える相手は読者として扱う。
2. 前書きなら、読者が共感しやすい課題感、著者の動機、作るもの、到達点、進め方を一問ずつ確認する。章なら、その章で読者が得る具体的な変化と根拠を同じ粒度で取材する。
3. 骨子に作者の動機が書かれていれば、その位置を維持する。`?` なら冒頭候補を3本出し、ユーザーに一つずつ質問する。
4. 段落数と段落の役割を提案し、各段落の確認済み事実を固定する。
5. ユーザーの回答を受けたら、その回答を材料に段落の一部を書き、実際の文面としてユーザーに示す。ここでは完成稿にせず、方向確認に足る長さだけ書く。課題感、解決策、実装のどこを書いているかを明示する。
6. その部分への反応を見てから、次の質問を一つだけ出す。質問を重ねる前に、前回の回答が文面にどう反映されたかを明示する。
7. 段落より小さい単位で本文を起こす。事実と異なる肉付け、例え話、強い断定、締め方は先に確認する。
8. 段落が完成するたびに、役割、使った事実、読者に増えた判断材料を示して確認する。
9. 全体をまとめてからではなく、各段落を起こすたびに `humanizer-ja` を当てて進める。
10. 進行中も次の監査を行う。

## 前書き監査

完成稿を出す前に、本文だけを読んで次を確認する。

- [ ] 一文で「誰が、何を作るか・できるようになるか、なぜこの方法か」を答えられるか。
- [ ] 作るもの、到達点、方法の理由、対象読者、前提または対象外、読み方を、必要な範囲で取り出せるか。
- [ ] 冒頭が一般論、流行語、雰囲気の説明、汎用的な呼びかけになっていないか。
- [ ] 各段落に、固有の物・行為・場面・制約・結果のいずれかがあるか。
- [ ] 技術説明の各段落が、読者の課題や疑問に対する答えになっているか。
- [ ] 前書きの各段落が、読者の課題感・作者の動機・書籍の判断材料を進めているか。
- [ ] 本文が丁寧語で統一されているか。読者を「君」、著者を「僕」で固定していないか。
- [ ] 各段落が、新しい読者判断を一つ進めているか。前段の言い換えだけになっていないか。
- [ ] トーンの説明を消しても、著者の観察や声が残るか。
- [ ] 実在しない章立て、成果、読者への約束を補っていないか。

一つでも満たせない場合は、表現を飾る前に取材か段落設計へ戻る。
